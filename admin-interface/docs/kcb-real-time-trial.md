## 1. What is being built

An instant payment notification (IPN) is a message KCB sends to a web address that
SmartMoney owns, every time money moves on a watched account. SmartMoney does not poll
and does not ask the bank for a balance. The bank pushes, SmartMoney receives, checks
the signature, stores the event and shows it on the dashboard.

The full path is:

```text
   money moves on the account
              |
              v
   KCB signs the notification with the KCB private key
              |
              v
   POST  <PUBLIC_BASE_URL>/api/v1/webhooks/kcb
         header: Signature
         body:   JSON
              |
              v
   SmartMoney verifies the signature against the KCB public key
              |
              v
   the event is stored, then processed
              |
              v
   the dashboard, Bank Integrations page and Reports page read the stored result
```

## 2. Three levels of testing, and what each one can prove

These are separate things. Being clear about which level you are on prevents a lot of
confusion about why your own account does not appear to be watched.

| Level | What it exercises | Needs KCB credentials | Can it watch your own account |
| --- | --- | --- | --- |
| 1. Local rehearsal | The exact receive, verify, store and display path, using a notification this repository signs itself | No | No |
| 2. KCB BUNI sandbox | The real KCB network path, with a notification KCB sends | Yes, sandbox Key and Secret | No |
| 3. Production account | Notifications generated by real activity on your own KCB account | Yes, a production subscription with the account enabled | Yes |

The important limitation to understand before you start: the BUNI sandbox is a test
environment with its own accounts. It does not observe your personal or business KCB
account. Seeing money you actually send and receive requires Level 3, where the bank
enables the notification service on the specific account.

## 3. Level 1: local rehearsal, works today

This is the level that is already working. It sends a notification that is signed with
SHA256withRSA exactly the way the specification describes, so the service performs a
real signature check rather than skipping it.

### 3.0 Start from zero

If you want the dashboard to begin at zero before your own trial, stop the service and
move the database aside. It is moved, never deleted, so the previous contents can be
restored.

```powershell
.\tools\reset-data.ps1
```

Type `yes` when it asks. The file it produces is written to `backend\data\backup` with a
timestamp in its name, and the script prints the exact path.

### 3.1 Start the service

```powershell
cd "C:\Users\user\Desktop\ECLECTICS\SM-Intelligence\admin-interface\backend"
.\run-local.ps1
```

Leave that window open. The script prints the credential state and the addresses to give
the bank.

### 3.2 Confirm the endpoint answers

In a second window:

```powershell
Invoke-RestMethod http://localhost:8080/api/v1/webhooks/kcb
```

You should see a short plain text confirmation naming KCB. That address is live.

### 3.3 Send a signed notification

```powershell
cd "C:\Users\user\Desktop\ECLECTICS\SM-Intelligence\admin-interface\backend"
.\tools\send-kcb-notification.ps1 -Amount 15000 -Direction Credit -Count 3
```

The first run creates a rehearsal key pair under `backend\keys\`, which git ignores,
signs the body and posts it. Each notification should answer HTTP 200 with the
acknowledgement body required by the BUNI specification:

```json
{"transactionID":"KCB-...","statusCode":"0","statusMessage":"Notification received successfully"}
```

### 3.4 Turn on signature checking

The service only reports a notification as verified when it has a public key to check
against. Point it at the rehearsal key once:

```powershell
.\tools\send-kcb-notification.ps1 -UsePublicKey
```

That writes `KCB_PUBLIC_KEY=keys/kcb-rehearsal-public.pem` into `.env.local`. Restart the
service so the key is loaded, then send another notification. It now shows as verified.

### 3.5 See the result

```powershell
Invoke-RestMethod http://localhost:8080/api/v1/admin/stats
Invoke-RestMethod http://localhost:8080/api/v1/admin/bank-integrations
```

In the admin interface, open Dashboard to see the notification count, the volume chart
and the recent activity list, and Bank Integrations to see the per bank counters.

### 3.6 What a successful rehearsal looks like

The three figures below were captured from this repository on 15 September 2026, after
12 rehearsed notifications:

```text

failed                0
```

## 4. Level 2: the KCB BUNI sandbox

### 4.1 What is already done in this repository

| Piece | State |
| --- | --- |
| Notification endpoint `/api/v1/webhooks/kcb` | Implemented, returns the exact acknowledgement the specification requires |
| Signature verification, SHA256withRSA | Implemented, accepts a PEM block, a path to a `.pem` file, or a base64 X.509 key |
| Idempotency on the notification reference | Implemented, a repeated reference is stored once |
| OAuth client credentials for the BUNI token endpoint | Implemented, supporting both the Authorization header and form body |
| Per bank counters and platform statistics | Implemented |

### 4.2 What is missing, and who has to supply it

Three values are needed. Only you can obtain them from the BUNI portal.

| Value | Where it comes from | Where it goes |
| --- | --- | --- |
| KCB sandbox Key and Secret | The application page, using Generate Key. The portal currently reports that no key has been generated for the application | `KCB_CLIENT_KEY` and `KCB_CLIENT_SECRET` in `.env.local` |
| KCB public key | The KCB integration team or the product documentation. The specification says to verify with the KCB public key, but does not publish it | `KCB_PUBLIC_KEY` in `.env.local` |
| The exact callback address to register | You create it, from your tunnel | The Callback URL field in the BUNI application, described in 4.4 |

Until the Key and Secret exist, `/api/v1/admin/bank-integrations` reports the KCB
notification channel as healthy if notifications arrive, and the API status as
`PENDING`, which is the honest answer for an integration with no credentials loaded.

### 4.3 Open a public tunnel

KCB cannot reach `localhost`. `cloudflared` is already installed on this machine at
`C:\Program Files (x86)\cloudflared\cloudflared.exe`. If the `cloudflared` command is
reported as not recognised, the PATH has not been refreshed in that window. Either open
a new terminal, or call it by full path:

```powershell
& "C:\Program Files (x86)\cloudflared\cloudflared.exe" tunnel --url http://localhost:8080
```

The window stays open and prints an address such as
`https://something.trycloudflare.com`. The address changes every time the tunnel
restarts, so copy it fresh each session.

Note on this machine: a DNS resolver warning from cloudflared
(`Failed to initialize DNS local resolver`) has been seen while the tunnel still
forwarded traffic. Confirm the tunnel works with
`Invoke-RestMethod <tunnel>/actuator/health` before registering anything.

### 4.4 Register the address with KCB

1. Put the tunnel address into `.env.local` as `PUBLIC_BASE_URL` and restart the service.
2. Confirm the printed notification address answers, for example
   `https://<tunnel>/api/v1/webhooks/kcb`.
3. In the BUNI application, set the Callback URL to
   `https://<tunnel>/api/v1/webhooks/kcb`. If the instant payment notification product
   has its own registration field, use the same address there.
4. Generate the sandbox Key and Secret for the application, then copy them into
   `.env.local`.
5. Restart the service. `run-local.ps1` prints whether each value was loaded, so a
   missing one is visible immediately.

### 4.5 Send the test notification

In the BUNI try out console for the instant payment notification product:

1. Fill the `Signature` header. The console signs with the KCB private key, so if you
   are asked for a value here, this is the one field the portal must provide.
2. Paste a JSON body for a credit and execute. Expect HTTP 200 with the acknowledgement
   body shown in 3.3.
3. Execute again with a debit body.
4. Check `Invoke-RestMethod http://localhost:8080/api/v1/admin/stats` and the dashboard.

### 4.6 One uncertainty to close

The specification excerpt in hand documents the acknowledgement SmartMoney must return.
It does not document the field names of the request body KCB sends. The endpoint accepts
several common reference field names (`transactionID`, `transactionId`,
`transaction_id`, `transactionReference`, `transactionRef`, `reference`, `id`), so an
unexpected one degrades to the stored event id rather than failing.

Send one body from the sandbox, then read it back so the exact shape can be recorded and
the parser tightened:

```powershell
$stats = Invoke-RestMethod http://localhost:8080/api/v1/admin/stats
$stats.recent | Select-Object -First 1
```

The full body is stored with each event, so it can be inspected directly from the
`webhook_event` table.

## 5. Level 3: notifications from your own KCB account

This is the level that answers "when I send and receive money". It is a commercial and
onboarding step, not a code step.

1. Ask the KCB relationship manager or the BUNI team to enable the transaction
   notification product on the specific account number, in production.
2. Supply the production notification address, which must be a public HTTPS address that
   is always available. A tunnel is not suitable for production.
3. Set `KCB_ENV=PRODUCTION` and the production token endpoint, then load the production
   Key and Secret.
4. Load the KCB production public key so signatures can be verified.
5. Send a small real payment to the account and confirm it appears.

Until step 1 is completed, no software change will make your own account visible to the
sandbox.

## 6. Where to put each value

One file, `admin-interface\backend\.env.local`, which git ignores. The interactive
alternative is `.\set-credentials.ps1`, which asks for each value and writes the file.

| Variable | Purpose |
| --- | --- |
| `KCB_CLIENT_KEY` | Sandbox or production Key from BUNI |
| `KCB_CLIENT_SECRET` | The matching Secret |
| `KCB_PUBLIC_KEY` | KCB public key used to verify the `Signature` header |
| `KCB_TOKEN_URL` | Optional, defaults to `https://accounts.buni.kcbgroup.com/oauth2/token` |
| `KCB_AUTH_STYLE` | Optional, `basic` to send credentials in the Authorization header, `body` for form fields |
| `PUBLIC_BASE_URL` | The public address the bank can reach. Prints the notification and redirect addresses |
| `PERMIT_ALL` | Development only. Set to `false` before any shared deployment |

## 7. Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `The term 'cloudflared' is not recognized` | The PATH was set by the installer but this terminal predates it | Open a new terminal, or call `C:\Program Files (x86)\cloudflared\cloudflared.exe` by full path |
| The tunnel closes immediately | The tunnel window was closed, or the free session expired | Start it again and copy the new address. It changes every restart |
| `Failed to connect to localhost port 8080` | The service is not running | Start it with `.\run-local.ps1` and leave that window open |
| The dashboard shows zero after a notification was accepted | The service was restarted and `PUBLIC_BASE_URL` or another value was reloaded incorrectly, or the wrong instance answered | Confirm one instance only is listening on 8080, then reload the page |
| Signature shows as not checked | No public key is loaded | Set `KCB_PUBLIC_KEY`, restart, and send another notification |
| `415 Unsupported Media Type` when calling an admin endpoint | An older build required a JSON content type on endpoints that now accept any | Rebuild the backend, or send `-ContentType 'application/json' -Body '{}'` |
| Two notifications for one payment | The reference sent by the bank changed between deliveries | Check the stored bodies. Deduplication keys on the bank plus the reference |
