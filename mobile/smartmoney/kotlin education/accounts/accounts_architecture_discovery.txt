1. EXECUTIVE SUMMARY
================================================================================
This report presents an evidence-based, deep architectural discovery of the Accounts
subsystem across the SmartMoney mobile application and its corresponding backend
microservices.

Key Architectural Findings:
1. Architectural Dualism: Two parallel account abstractions coexist in the system:
   - "Account" (Generic/Manual/Energy Account): Originates from the Spring Boot
     accounts-service (:8082, PostgreSQL table "accounts"). It supports ledger
     balance, available balance, credit limits, outstanding credit, and manual
     entry.
   - "BankAccount" (Institutional Bank Card/Link): Focuses on financial institution
     links (KCB, NCBA, Stanbic, Equity, M-PESA) managed primarily via the
     bank-integration-service (:8090, PostgreSQL table "account_links").
2. Dual Repositories & Hybrid Routing:
   - AccountRepository / AccountRepositoryImpl handles generic account fetching,
     syncing, and deletion via accounts-service REST endpoints (/api/accounts).
   - BankAccountRepository / BankAccountRepositoryImpl acts as a hybrid router.
     When linking supported Tier-1 Kenyan banks (KCB, NCBA, Stanbic, Equity), it
     routes the creation request to bank-integration-service
     (POST /api/v1/admin/account-links). For other institutions or offline fallback,
     it routes to accounts-service (POST /api/accounts) or creates an offline
     record directly in Room SQLite.
3. Local-First Caching Architecture:
   - The UI never depends on synchronous remote HTTP calls during rendering.
   - All account presentations in Jetpack Compose observe Kotlin StateFlow streams
     backed by Room database queries (AccountDao.getAccountsForUser(userId)).
   - Local database mutations (Room SQLite "energy_cache_database", version 4)
     immediately update the UI via reactive Flow pipelines.
4. Asynchronous Ledger Synchronization:
   - External bank instant payment notifications (IPNs / webhooks) land at
     bank-integration-service (:8090), which normalizes the payload into
     NormalizedTransactionEntity, persists it, forwards transactions to
     transactions-service (:8083), and invokes PATCH /api/accounts/{id}/balance/adjust
     on accounts-service (:8082) using an internal trust token (X-Internal-Token).
5. Post-Authentication Pre-Hydration:
   - Upon successful user login, WarmUpSyncViewModel runs a parallel pre-hydration
     routine in the background (syncing accounts and transactions concurrently
     using async/awaitAll) while displaying a staged 3-second progress indicator,
     guaranteeing immediate responsiveness when DashboardScreen appears.
6. Legacy Artifacts:
   - Traces of deprecated Supabase/Postgrest client calls remain in orphaned classes
     (AccountConnectionRemoteDataSource, AccountConnectionRepositoryImpl,
     BankAccountDto comments), though active production routing has fully transitioned
     to the unified Production Render Gateway (https://api-gateway-cbby.onrender.com/).

3. EXISTING ARCHITECTURAL PATTERNS
================================================================================
The codebase demonstrates several modern Android and distributed systems patterns,
though some boundaries exhibit pragmatic coupling:

1. MVVM (Model-View-ViewModel):
   - Presentation logic is decoupled from Jetpack Compose UI via AccountViewModel.
   - UI components (AccountScreen, BankAccountCard) are stateless or receive state
     via hoisted parameters and emit lambdas for user gestures.
   - Compose observes state via collectAsState() on StateFlow<AccountUiState>.

2. Clean Architecture (Partial / Pragmatic):
   - Clear separation between UI Layer (ui/accounts), Domain Layer (domain/model,
     domain/repository), and Data Layer (data/local, data/remote, data/repository).
   - Domain layer contains pure Kotlin models (Account, BankAccount) with zero
     Android SDK or Room annotations, except @Immutable for Compose compiler optimization.
   - Note on Use Cases: There is NO intermediate UseCase or Interactor layer in the
     mobile project. The ViewModels directly consume Repository interfaces
     (AccountRepository, BankAccountRepository).

3. Offline-First Repository Pattern with Reactive Caching:
   - Repository methods return cold Flow streams originating from Room DAOs.
   - Network fetches update the Room database via upsert operations; Room's internal
     invalidation tracker automatically notifies the Flow, propagating fresh data
     to the ViewModel and UI without manual polling loops.

4. Hybrid Remote Routing (Facade / Dispatcher Pattern):
   - BankAccountRepositoryImpl acts as a smart router. Depending on whether an
     institution is classified as a supported integrated bank (KCB, NCBA, Stanbic,
     Equity), it routes to bank-integration-service or accounts-service, providing
     fallback resilience if the specialized integration service is unavailable.

5. Optimistic Concurrency & Atomic Database Operations:
   - On the backend, accounts-service uses JPA @Version optimistic locking to
     prevent dirty writes during account modifications.
   - For high-throughput transaction movements, it bypasses entity-level read-modify-write
     by executing an atomic SQL UPDATE (AccountRepository.adjustAvailableBalance)
     guaranteeing that concurrent webhook deliveries never overwrite one another.

6. Anti-Corruption Layer / Adapter Mapping:
   - DTOs, Room Entities, and Domain models are segregated.
   - Explicit conversion extensions (toDomain(), fromDomain(), toBankAccount())
     prevent API schema changes from rippling across presentation logic.

7. Manual Dependency Injection (Container Pattern):
   - No Hilt or Dagger annotation processing is employed.
   - Dependencies are managed via AppContainer / DefaultAppContainer using lazy
     initialization and supplied to ViewModels via custom ViewModelProvider.Factory
     implementations.

7. DOMAIN LOGIC AND BUSINESS RULES
================================================================================
1. Account Number Masking:
   - Implemented in BankAccount.maskedAccountNumber and AccountEntity.maskedIdentifier:
     If the number already begins with "*", return verbatim.
     If length > 4, format as "**** " + trimmed.takeLast(4).
     If length <= 4, format as "**** " + trimmed.
   - On the backend, PlatformServicesClient masks with "***" + last4, and
     ManualAccountController masks with "•••• " + last4.

2. Monetary Precision Rules:
   - Balances must never be stored, calculated, or transmitted as Double or Float.
   - Mobile and backend enforce java.math.BigDecimal with standard string serialization.
   - Database columns in PostgreSQL are typed as NUMERIC(19,4) to comply with
     international banking reconciliation standards.

3. Institution & Key Normalization:
   - User-facing labels are uppercase / titlecase (e.g. "KCB", "NCBA", "Stanbic", "Equity").
   - Internal API endpoints and webhook route parameters are lowercase (e.g. "kcb", "ncba").

4. Multi-Tenant User Isolation & Aliasing:
   - Mobile client handles user IDs that may be plain strings (from mock/legacy auth)
     or valid UUIDs.
   - In BankAccountRepositoryImpl, effectiveUserId is computed:
     try { UUID.fromString(currentUserId).toString() }
     catch (_: Exception) { UUID.nameUUIDFromBytes(currentUserId.toByteArray()).toString() }
   - To prevent Room queries from failing if a query uses the raw string instead
     of the UUID, BankAccountRepositoryImpl writes dual records to Room:
     the primary entity under currentUserId and an alias entity under effectiveUserId
     with id "${accountId}_alias".

5. Global Single-Registration Rule:
   - Implemented in accounts-service V1__initial_schema.sql:
     CONSTRAINT unique_provider_account UNIQUE (institution, provider_account_id)
   - An account number at a specific bank can only belong to one user across the entire
     system. If User A registers account 12345678 at KCB, User B attempting to add
     it will be rejected with HTTP 409 Conflict ("This account number is already
     registered to another user").

6. SHA-256 Fingerprinting for Self-Entered Accounts:
   - To protect customer privacy while preserving the unique constraint,
     ManualAccountController hashes manual account numbers:
     AccountService.fingerprint(bank, accountNumber) = sha256("account:" + bank + ":" + accountNumber.trim())
   - The plain account number is NEVER persisted in the database for manual entries.

9. LOCAL PERSISTENCE
================================================================================
1. Database Architecture:
   - Database class: com.example.smartmoney.data.local.database.AppDatabase
   - Database name: "energy_cache_database"
   - SQLite version: 4
   - Tables: accounts, account_connections, transactions, notifications, users.
   - Type Converters: Converters class converts BigDecimal to plain string via
     toPlainString() and parses via BigDecimal(string), guaranteeing no precision drift.

2. Table Definition: accounts (AccountEntity)
   - Primary Key: id (String / UUID)
   - Indices:
     * Index(value = ["userId"]) -> Scopes all user queries
     * Index(value = ["accountId"]) -> Quick lookup by external account number
     * Index(value = ["accountStatus"]) -> Filters active vs closed
     * Index(value = ["userId", "createdAt"]) -> Fast chronological ordering
   - Balance columns: ledgerBalance, availableBalance, creditOutstanding, creditLimit, availableCredit.

3. Reactive Observation:
   - AccountDao.getAccountsForUser(userId: String): Flow<List<AccountEntity>>
   - When any upsert or update occurs in SQLite, Room emits a new List<AccountEntity>
     to all active Flow collectors.
   - BankAccountRepositoryImpl maps this via .map { list -> list.map { it.toBankAccount() } }
     and dispatches on dispatchers.default.

4. Balance Updates & Mutation API:
   - Direct Balance Set:
     UPDATE accounts SET availableBalance = :newBalance, ledgerBalance = :newBalance
     WHERE userId = :userId AND (id = :accountId OR accountId = :accountId)
   - Atomic Balance Delta Adjustment:
     UPDATE accounts SET availableBalance = availableBalance + :delta,
     ledgerBalance = ledgerBalance + :delta
     WHERE userId = :userId AND (id = :accountId OR accountId = :accountId)
   - Institution-level Adjustment:
     UPDATE accounts SET availableBalance = availableBalance + :delta,
     ledgerBalance = ledgerBalance + :delta
     WHERE id = (SELECT id FROM accounts WHERE userId = :userId AND
     (UPPER(institution) = UPPER(:institution) OR UPPER(accountName) LIKE '%' || UPPER(:institution) || '%')
     ORDER BY createdAt ASC LIMIT 1)

5. Cascade Cleanup on Account Removal:
   - When an account is removed in BankAccountRepositoryImpl or AccountRepositoryImpl:
     1. localDao.deleteAccountById(id)
     2. transactionDao.deleteTransactionsForAccount(userId, id)
     This prevents orphaned transactions from lingering in the local ledger.

6. Destructive Migration Risk:
   - AppDatabase specifies: .fallbackToDestructiveMigration(dropAllTables = true).
   - If the database schema version is incremented without an explicit Migration
     implementation, Room wipes all SQLite tables, causing total local data loss
     until the next network pre-hydration sync.

11. BACKEND PROCESSING AND DATABASE OPERATIONS
================================================================================
1. accounts-service Architecture:
   - Framework: Spring Boot 3 WebMVC, Spring Data JPA, Flyway, PostgreSQL.
   - Schema: smi_accounts database, table accounts.
   - Controllers:
     * AccountController: Standard CRUD for authenticated users and internal services.
     * ManualAccountController: Handles manual card registration with SHA-256 fingerprinting.
   - Account Creation Lifecycle:
     1. AccountController.createAccount() checks caller identity via AccountIdentity.
        If caller is not internal service (lacks X-Internal-Token), request.userId
        is forcibly overwritten with identity.owner(authorization).
     2. AccountService.createAccount() checks findHolder(institution, providerAccountId).
        If already held by any user, throws DuplicateAccountException (409 Conflict).
     3. Instantiates Account JPA entity with status ACTIVE and connection status CONNECTED.
     4. Saves to PostgreSQL via AccountRepository.save().

2. Atomic Balance Adjustment Pipeline:
   - PATCH /api/accounts/{id}/balance/adjust
   - Protected: Only callers providing X-Internal-Token matching INTERNAL_SERVICE_TOKEN
     are authorized; all other callers receive 403 Forbidden.
   - Executes SQL UPDATE in one statement:
     UPDATE Account a SET a.availableBalance = a.availableBalance + :delta,
     a.ledgerBalance = a.ledgerBalance + :delta, a.lastUpdated = :now WHERE a.id = :id
   - Returns updated AccountResponse entity.

3. bank-integration-service Linking & Delivery Pipeline:
   - AccountLinkController.link():
     * If caller is a customer (ROLE_CUSTOMER), verifies platform.ownsAccount(userId, accountId, institution, accountNumber).
       If false, throws 403 Forbidden ("You can only link an account you have saved yourself").
     * Calls AccountLinkService.link().
     * If existingAccountId is not provided, calls platform.ensureAccount() which POSTs
       to accounts-service (/api/accounts) with X-Internal-Token.
     * Persists AccountLinkEntity in PostgreSQL (smi_bank_integrations).
     * Dispatches any earlier pending webhook transactions via deliverPending().
   - Incoming Bank Webhooks (KCB, NCBA, Stanbic, Equity):
     * Bank sends Instant Payment Notification (IPN) to /api/v1/webhooks/{bank}.
     * Webhook controller validates RSA/HMAC signature and parses payload into NormalizedTransactionEntity.
     * Checks idempotency: if transactionReference was already processed, acknowledges 200 OK.
     * Dispatches transaction to transactions-service (:8083) via PlatformServicesClient.recordTransaction().
     * Upon confirmation (Recorded.CREATED), calls PlatformServicesClient.adjustBalance(accountId, delta),
       which updates accounts-service.
   - Outage Recovery:
     * If downstream accounts-service or transactions-service is down, the movement's
       forwardedAt timestamp remains null.
     * AccountLinkService runs a scheduled background task every 5 minutes:
       @Scheduled(initialDelayString = "PT5M", fixedDelayString = "PT5M")
       public void retryPending()
       Retries delivery until services recover, guaranteeing zero lost financial movements.

12. AUTHENTICATION AND AUTHORIZATION
================================================================================
1. Authentication Architecture:
   - Mobile:
     User signs in via AuthRemoteDataSource.login(). JWT access token is stored in
     UserPreferencesRepository (smartmoney_prefs).
     RetrofitClient.tokenProvider supplies token to authInterceptor, injecting
     Authorization: Bearer <jwt> on all HTTP calls.
   - Backend:
     accounts-service does not maintain internal JWT verification secrets.
     Instead, AccountIdentity.owner(authorization) calls identity-service:
     GET /api/auth/me with the incoming Authorization header.
     If valid, identity-service returns user JSON containing UUID id.
     If expired or missing, AccountIdentity throws ResponseStatusException(HttpStatus.UNAUTHORIZED).

2. Authorization Boundaries:
   - User Isolation:
     In AccountController, getAccountsByUserId(), getAccountById(), updateBalance(),
     and deleteAccount() verify that the requested account's userId matches the
     authenticated caller's UUID. Attempting to access another user's account returns
     404 Not Found or 403 Forbidden.
   - Internal Service Trust Delegation:
     Calls between microservices (e.g. bank-integration-service -> accounts-service)
     pass header X-Internal-Token: ${INTERNAL_SERVICE_TOKEN}.
     When present and verified by AccountIdentity.isInternalService(token),
     accounts-service permits administrative operations (such as balance adjustments
     or linking on behalf of a user) without requiring an interactive user session.
   - Customer Link Authorization:
     In bank-integration-service, AccountLinkController checks caller authorities:
     A customer can ONLY link an account if accounts-service already holds a matching
     account record for them (verified by platform.ownsAccount()). This prevents
     malicious users from linking stranger bank account numbers to steal notifications.

13. COROUTINES AND ASYNCHRONOUS EXECUTION
================================================================================
1. Dispatcher Architecture:
   - Abstracted via com.example.smartmoney.core.coroutine.DispatcherProvider:
     * io: CoroutineDispatcher = Dispatchers.IO
     * default: CoroutineDispatcher = Dispatchers.Default
     * main: CoroutineDispatcher = Dispatchers.Main
     * unconfined: CoroutineDispatcher = Dispatchers.Unconfined
   - Production uses DefaultDispatcherProvider; unit tests inject TestDispatcherProvider
     backed by StandardTestDispatcher or UnconfinedTestDispatcher for deterministic testing.

2. Coroutine Scope Lifecycle:
   - ViewModels use viewModelScope. All launched jobs are automatically cancelled
     when the ViewModel is cleared (onCleared()).
   - Long-lived database operations (e.g. database clearing on logout in MainActivity)
     use CoroutineScope(Dispatchers.IO).launch.

3. Flow Execution & Thread Hopping:
   - Flow streams from Room DAOs execute SQLite queries on Room's query executor pool.
   - BankAccountRepositoryImpl applies .flowOn(dispatchers.default) during entity-to-domain
     mapping to keep the Android main thread free of CPU mapping overhead.
   - ViewModel state collection uses .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), ...).
   - In AccountViewModel, network operations run on dispatchers.io, then explicitly
     switch via withContext(dispatchers.main) before executing caller UI lambdas
     (onSuccess, onError).

4. Parallel Pre-Hydration Pipeline:
   - In WarmUpSyncViewModel:
     coroutineScope {
         val accJob = async { accountRepository.syncAccounts(userId) }
         val txJob = async { transactionRepository.syncTransactions(userId = userId) }
         awaitAll(accJob, txJob)
     }
   - Both network requests execute concurrently over OkHttp's asynchronous thread pool,
     cutting total sync latency in half.

14. ERROR HANDLING AND FAILURE SCENARIOS
================================================================================
1. Complete Offline Scenario:
   - When device is completely disconnected from internet:
     * AccountScreen continues to display cached accounts from Room SQLite without errors.
     * If user pulls to refresh, AccountRepositoryImpl.syncAccounts() catches
       IOException/SocketTimeoutException and returns Result.failure(e).
     * AccountViewModel catches failure, dismisses loading spinner, and sets _bankAccountError.
     * If user adds a bank account while offline, BankAccountRepositoryImpl catches network
       failure and executes offline fallback: generates a UUID, creates Account model with
       dataSource = "MANUAL", saves to Room AccountDao, and updates UI state immediately.

2. Network Timeout & Server 5xx Outages:
   - OkHttp 60-second timeouts prevent indefinite socket hangs.
   - AccountRemoteDataSource parses error envelopes via parseErrorMessage():
     Extracts Spring Boot JSON fields: "message", "details", or "error".
     If response body is unparseable HTML or plain text, returns "HTTP $code: $message".
   - Surfaced to user via Material 3 SnackbarHostState.showSnackbar().

3. Duplicate Account Conflicts (HTTP 409):
   - When an account number is already linked globally, backend returns 409 Conflict.
   - Bank-integration-service catches 409: checks if the existing account belongs to
     the same user (a re-link); if so, reactivates it to ACTIVE. If it belongs to
     another user, throws refusal message to the client.

4. Unauthenticated / Session Expiry (HTTP 401 / 403):
   - When auth token is invalid or expired, backend returns 401 Unauthorized.
   - MainActivity handles user logout by calling appContainer.database.clearAllTables()
     and resetting UserProfileManager and authViewModel.

5. Concurrent Balance Modifications:
   - Handled at database level:
     * Room SQLite: DAO balance adjustments execute within SQLite transactions.
     * Backend PostgreSQL: Atomic UPDATE ... SET availableBalance = availableBalance + :delta
       eliminates read-modify-write lost updates.

15. PERFORMANCE AND RELIABILITY FINDINGS
================================================================================
The investigation identified several concrete findings across performance and reliability:

Finding 1: Architectural Dualism (Account vs BankAccount)
- Source Path:
  mobile/.../domain/model/Account.kt & mobile/.../domain/model/BankAccount.kt
  mobile/.../data/repository/AccountRepositoryImpl.kt & mobile/.../data/repository/BankAccountRepositoryImpl.kt
- Evidence: Both repositories are injected into AccountViewModel and HomeViewModel.
  AccountScreen only displays bankAccounts, while AccountRepository is used for syncing.
- Impact: High architectural complexity, redundant data conversions, and potential
  for state divergence between the two repositories.

17. CONFIRMED ISSUES AND POTENTIAL RISKS
================================================================================
1. [CONFIRMED ISSUE] Alias Record Pollution in Room SQLite:
   BankAccountRepositoryImpl writes duplicate rows with suffix "_alias" into the
   accounts table to bridge String and UUID representations of user IDs. If queries
   in other components (such as reports or analytics) fail to filter out "_alias"
   keys, account counts and balances will be duplicated.

2. [CONFIRMED ISSUE] Orphaned Supabase AccountConnection Pipeline:
   AccountConnectionRemoteDataSource and AccountConnectionRepositoryImpl remain in
   the project and import deprecated Supabase packages, creating confusion about
   the system's single source of truth.

3. [CONFIRMED ISSUE] Dead AccountCard Composable:
   AccountScreen.kt contains 56 lines of dead code implementing an unused AccountCard
   composable.

4. [POTENTIAL RISK] Direct Balance Mutation vs Ledger Inconsistency:
   AccountDao exposes updateAccountBalance() and adjustAccountBalance() which modify
   the account balance directly without creating a corresponding TransactionEntity.
   MpesaTransactionIngestionService and BankAccountRepositoryImpl utilize these
   methods, creating potential discrepancies between total account balance and the
   sum of ledger transactions.

5. [POTENTIAL RISK] Destructive Database Migration in Production:
   AppDatabase uses fallbackToDestructiveMigration(dropAllTables = true). Any schema
   change without migration scripts will purge offline user data.
