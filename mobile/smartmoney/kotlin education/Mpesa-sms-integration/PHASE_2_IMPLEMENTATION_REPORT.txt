3. INGESTION FLOW AND DEPENDENCY WIRING
--------------------------------------------------------------------------------
The ingestion workflow is completely decoupled from parsing and telephony:

Step 1: Receipt Reference Validation
- Normalizes reference to uppercase trimmed string.
- Validates that the reference is non-blank and conforms to M-PESA receipt syntax
  (alphanumeric, 5-20 characters, e.g. "QH789XYZ12").
- Rejects invalid input immediately with `MpesaIngestionResult.InvalidMovement`.

Step 2: Monetary Invariant Validation
- Verifies `movement.amount > BigDecimal.ZERO`.
- Preserves exact `BigDecimal` scale without floating-point conversion loss.
- Rejects zero or negative amounts with `MpesaIngestionResult.InvalidMovement`.

Step 3: User ID Resolution
- Resolves the target user ID from the explicit parameter or via `userIdProvider`
  (hooked to `authRepository.currentUserId()`).
- Rejects with `MpesaIngestionResult.MissingAccount` if no authenticated user session exists.

Step 4: Local M-PESA Account Resolution
- Searches user accounts via `AccountDao` matching `institution = "M-PESA"` / `"MPESA"`
  or `accountType in ["MOBILE_MONEY", "WALLET"]`.
- If an account ID is specified, verifies that it exists and belongs to the user.
- If no account exists, returns `MpesaIngestionResult.MissingAccount`.

Step 5: Concurrency Control and Pre-Check
- Acquires process-level coroutine `Mutex` (`ingestionMutex.withLock`).
- Executes `findTransactionByProviderIdOrId` query using `reference` and deterministic
  primary key `mpesa_$reference`.
- If a record is found, returns `MpesaIngestionResult.Duplicate` without attempting insert.

Step 6: Lossless Domain-to-Entity Mapping
- Formats timestamp to ISO-8601 string.
- Builds a structured `description` preserving all auxiliary fields (counterparty name,
  phone number, biller account, reversal original reference, and fee).
- Generates `TransactionEntity` with `id = "mpesa_$reference"` and `providerTransactionId = reference`.

Step 7: Atomic Database Insertion
- Calls `transactionDao.insertTransaction(entity)`.
- If an SQLite constraint violation occurs due to concurrent execution, safely catches
  `SQLiteConstraintException`, verifies duplicate existence, and returns `Duplicate`.
- On unexpected I/O or Room errors, returns `MpesaIngestionResult.DatabaseError`.
- On success, returns `MpesaIngestionResult.Success(entity)`.

Dependency Wiring:
- Registered as a lazy singleton property in `AppContainer`:
  `override val mpesaTransactionIngestionService: MpesaTransactionIngestionService by lazy { ... }`
- Can be injected directly into future SMS workers or view models without creating
  parallel repository hierarchies or multiple database instances.


4. DUPLICATE-PREVENTION STRATEGY
--------------------------------------------------------------------------------
Guaranteeing idempotency and preventing duplicate transaction insertion is achieved
through a 4-layer defense:

1. Deterministic Primary Key:
   The entity primary key is mapped as `id = "mpesa_${reference.uppercase()}"`.
   Because SQLite intrinsically enforces primary key uniqueness, two transactions
   with the identical M-PESA receipt reference cannot coexist.

2. Query Pre-Check:
   Before attempting an insert, the service queries `TransactionDao` using
   `findTransactionByProviderIdOrId(reference, "mpesa_$reference")`. If a matching
   record is present, it returns `Duplicate` immediately without throwing an exception.

3. Process-Level Mutex:
   A thread-safe `Mutex` serializes ingestion calls within the application process,
   preventing race conditions from concurrent SMS broadcasts or parallel coroutines.

4. OnConflictStrategy.ABORT & Constraint Handling:
   The insert method uses `@Insert(onConflict = OnConflictStrategy.ABORT)`. Unlike
   `REPLACE` or `UPSERT`, this ensures that an existing transaction is never overwritten,
   corrupted, or reset if duplicate ingestion is attempted. If a constraint conflict
   triggers an `SQLiteConstraintException`, it is caught, verified, and safely reported
   as `Duplicate`.


5. ACCOUNT-ASSOCIATION STRATEGY
--------------------------------------------------------------------------------
1. Explicit Ownership:
   Every transaction is explicitly associated with an existing `AccountEntity` owned
   by the logged-in user. The ingestion service never defaults to orphan records or
   creates arbitrary accounts.

2. Resolution Order:
   - Target Account Override: If `targetAccountId` is supplied by the caller, the service
     verifies that the account belongs to the user and is a mobile money/M-PESA account.
   - Institution Match: Checks for an account with `institution = "M-PESA"` or `"MPESA"`.
   - Account Type Match: Scans the user's accounts for `accountType` equal to
     `"MOBILE_MONEY"` or `"WALLET"`, or containing `"M-PESA"`.

3. Rejection of Missing Accounts:
   If no eligible M-PESA account is discovered, the service returns
   `MpesaIngestionResult.MissingAccount`. It does NOT invent dummy accounts, guess user IDs,
   or silently reassign the transaction to a bank or savings account.

4. Preservation of Balances:
   In strict compliance with Phase 2 constraints, account balances (`currentBalance`)
   are NOT automatically mutated during ingestion. Double-entry ledger reconciliation
   will be handled in a dedicated phase once verified accounting logic is established.

     migration risks in this phase.

9. KNOWN LIMITATIONS AND UNRESOLVED DECISIONS
--------------------------------------------------------------------------------
1. Database Schema Indexing:
   `providerTransactionId` is currently not indexed as UNIQUE at the Room table level
   (uniqueness is enforced via primary key `id = "mpesa_$reference"`). In a future
   database version (v5), adding a dedicated unique index on `providerTransactionId`
   would further strengthen SQLite-level indexing.

2. Ledger & Balance Updates:
   Account balances are untouched. An accounting balance reconciliation service will
   need to be designed in Phase 4 once debit/credit posting rules are confirmed.

3. Offline Staging for Logged-Out Users:
   If an incoming SMS is received when no user session is active, the ingestion service
   will reject it with `MissingAccount`. In Phase 3, an unassigned local staging queue
   can be introduced to hold incoming movements until a user authenticates.

4. Dedicated Metadata Columns:
   Fields such as `fee`, `counterpartyPhone`, and `accountReference` are stored in
   the structured `description`. If future UI or reporting screens require filtering
   or querying by fee, dedicated columns can be added in a future Room migration.
