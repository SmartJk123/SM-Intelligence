1. CONFIRMATION OF THE SUSPECTED SIX-SECOND SYNCHRONIZATION LOOP
--------------------------------------------------------------------------------
The periodic synchronization loop reported in the investigation was CONFIRMED to
exist in `app/src/main/java/com/example/smartmoney/ui/home/HomeViewModel.kt`:

- Starting invocation: Called in `init` at line 176 (`startPeriodicSync()`).
- Implementation: Defined as `private fun startPeriodicSync()` (lines 200–214).
- Mechanics: Launched a coroutine on `viewModelScope` with a `while (isActive)` loop
  and `delay(6_000)` (6 seconds).
- Network payloads per tick:
    1. `transactionRepository.syncTransactions(userId = userId)`
       -> GET /api/v1/admin/demo/transactions (Bank Integration)
       -> GET /api/transactions?accountId={id} (for every linked account, unpaginated)
    2. `accountRepository.syncAccounts(userId)`
       -> GET /api/accounts?userId={userId}
- Cause of background execution: Because `HomeViewModel` is bound to the `MainActivity`
  lifecycle, its `viewModelScope` remains active whenever the app is minimized,
  switched away from, or the screen turns off. Android only destroys ViewModels
  when the host Activity is explicitly finished. Consequently, this loop executed
  every 6 seconds 24 hours a day, generating 30–50 HTTP requests per minute.

5. HOW ROOM-BACKED UI OBSERVATION WAS PRESERVED
--------------------------------------------------------------------------------
In `HomeViewModel.kt`, lines 78–86:
```kotlin
private val rawDataFlow = combine(
    accountRepository.getAccountsFlow(userId),
    bankAccountRepository.getBankAccounts(),
    transactionRepository.getTransactionsFlow(userId = userId),
    budgetsFlow
) { accounts, bankAccounts, transactions, budgets ->
    RawFinancialSnapshot(accounts, bankAccounts, transactions, budgets)
}
```
Verification of underlying sources:
- `accountRepository.getAccountsFlow(userId)` -> `localDao.getAccountsForUser(userId)`
  Returns a Room SQLite `Flow<List<AccountEntity>>`.
- `bankAccountRepository.getBankAccounts()` -> `localDao.getAccountsForUser(currentUserId)`
  Returns a Room SQLite `Flow<List<AccountEntity>>`.
- `transactionRepository.getTransactionsFlow(userId)` -> `localDao.getTransactionsForUser(targetUserId)`
  Returns a Room SQLite `Flow<List<TransactionEntity>>`.

The Home screen UI state (`uiState: StateFlow<HomeUiState>`) is derived directly from
`rawDataFlow` via `.stateIn(SharingStarted.WhileSubscribed(5_000))`. Whenever Room is
updated—whether from local M-PESA SMS ingestion, manual entries, or initial sync—the
Room SQLite triggers notify the flows immediately, recomputing the UI state reactively
with zero dependency on network polling.

8. UNRESOLVED RISKS & RECOMMENDED FOLLOW-UP WORK (PHASE 2+)
--------------------------------------------------------------------------------
1. N+1 Unpaginated Historical Ledger Downloads (`TransactionRemoteDataSource.kt`):
   When manual refresh or initial sync runs, `fetchTransactions()` iterates over each
   account individually, downloading the entire transaction history without a `since`
   or cursor parameter. Recommended Phase 2 fix: Implement incremental delta sync
   passing `since = lastSyncTimestamp`.
2. Production OkHttp Logging (`RetrofitClient.kt`):
   `HttpLoggingInterceptor.Level.BODY` is active unconditionally. Recommended Phase 2
   fix: Guard with `if (BuildConfig.DEBUG)`.
3. 401 Token Expiry Authenticator (`RetrofitClient.kt`):
   Add an `okhttp3.Authenticator` to handle token refresh and prevent retry storms
   on expired JWT sessions.
