1. EXECUTIVE SUMMARY
================================================================================
An exhaustive, evidence-based investigation was conducted on the SmartMoney Android
codebase to identify the root cause of excessive mobile data consumption occurring
when the application is idle or running in the background.

KEY FINDING:
The investigation discovered a CONFIRMED CRITICAL ARCHITECTURAL DEFECT in:
`com.example.smartmoney.ui.home.HomeViewModel` (lines 200–214).

An infinite coroutine loop (`startPeriodicSync()`) runs inside `viewModelScope`
with a sleep interval of only 6,000 milliseconds (`delay(6_000)`). Every 6 seconds,
it triggers remote synchronization for both transactions and accounts:
    1. GET /api/v1/admin/demo/transactions (Bank Integration Service)
    2. GET /api/transactions?accountId={id} (for EVERY account, unpaginated)
    3. GET /api/accounts?userId={id} (Accounts Service)

Because `HomeViewModel` is scoped to the `MainActivity` lifecycle, this coroutine
is NOT cancelled when the user minimizes the app, presses the Home button, switches
to other applications, or turns off the screen. Android activities remain in memory
(in `onStop` state) unless destroyed by the OS under extreme memory pressure.
Consequently, this loop continues firing 24 hours a day, generating:
    - 30 to 50 HTTP requests per minute
    - 1,800 to 3,000 HTTP requests per hour
    - 43,200 to 72,000 HTTP requests per day

DATA USAGE IMPACT ESTIMATE:
Assuming an average HTTP transaction payload (headers + TLS handshake + JSON) of
1.5 KB to 10 KB per request:
    - Minimum data burn: 64 MB to 108 MB per 24 hours (with empty transaction lists)
    - Realistic data burn: 200 MB to 720+ MB per 24 hours (with active transaction history)
    - Monthly data burn: 6 GB to 21+ GB of unmetered background data!

SECONDARY AMPLIFIERS IDENTIFIED:
1. N+1 Unpaginated Historical Queries: `TransactionRemoteDataSource` queries each
   account in an individual HTTP request, re-downloading the user's entire
   historical ledger without pagination, cursor, or `since` timestamp parameters.
2. Full Body Logging in Production: `RetrofitClient` includes an unconditional
   `HttpLoggingInterceptor.Level.BODY` interceptor, forcing OkHttp to buffer and
   string-encode every polling payload in memory.
3. Quadruple Simultaneous Initial Sync: On app login, `AccountViewModel`,
   `HomeViewModel`, and `WarmUpSyncViewModel` independently fire duplicate network
   calls to the same endpoints simultaneously without caching or deduplication.
4. Infinite 401 Unauthorized Failure Loop: If an auth token expires, the polling
   loop catches the exception and immediately retries 6 seconds later, forever.

OFFLINE INTEGRITY VERIFIED:
`MpesaNotificationListenerService` and local M-PESA SMS parsing were thoroughly
audited. The notification listener is 100% offline, executes strictly against the
local Room SQLite database, and initiates zero network requests. It is completely
exonerated from mobile data consumption.

4. CONFIRMED DEFECTS
================================================================================

--------------------------------------------------------------------------------
DEFECT ID: DEF-01 (CRITICAL)
--------------------------------------------------------------------------------
Classification: Confirmed Defect
File Path: app/src/main/java/com/example/smartmoney/ui/home/HomeViewModel.kt
Line Numbers: Lines 174–177, 200–214
Component: `HomeViewModel.startPeriodicSync()`
Description:
An unbounded `while (isActive)` loop executing on `viewModelScope` with a 6-second
delay (`delay(6_000)`). Every 6 seconds, it executes `syncTransactions()` and
`syncAccounts()`.

Code Excerpt:
```kotlin
// HomeViewModel.kt: Lines 174-177
init {
    refresh()
    startPeriodicSync()
}

// HomeViewModel.kt: Lines 200-214
private fun startPeriodicSync() {
    viewModelScope.launch(dispatchers.io) {
        while (isActive) {
            delay(6_000)
            try {
                transactionRepository.syncTransactions(userId = userId)
                if (userId.isNotBlank()) {
                    accountRepository.syncAccounts(userId)
                }
            } catch (_: Exception) {
                // Gracefully tolerate temporary network errors
            }
        }
    }
}
```

Why it causes excessive background mobile data:
1. `viewModelScope` is bound to the `ViewModel`, which is tied to `MainActivity`.
   When the user puts the app in the background (presses Home, navigates to another app,
   or the device screen turns off), the Activity enters `onStop`. The Activity is NOT
   destroyed. Therefore, `viewModelScope` remains active, and the coroutine continues
   executing every 6 seconds.
2. Every 6 seconds, 3 to 5+ HTTP requests are dispatched over the active network interface.
3. The cellular radio (LTE/5G) is never allowed to enter its low-power idle state
   (RRC Idle / DRX). The radio is held in continuous high-power state (RRC Connected /
   DCH), consuming both mobile data and battery rapidly.
4. If network errors occur, the empty `catch (_: Exception)` block silently swallows
   the error and immediately waits 6 seconds to repeat the failing request.

Estimated Data Impact:
At 5 requests/tick (user with 3 accounts) @ 1.5 KB/req = 7.5 KB every 6 seconds.
- 75 KB per minute
- 4.5 MB per hour
- 108 MB per 24 hours of pure idle background traffic.
With active transaction payloads of 20 KB:
- 100 KB every 6 seconds = 1 MB/min = 60 MB/hour = 1.44 GB/day!

Reproduction Scenario:
1. Launch SmartMoney and log in.
2. Press the Android Home button to background the application.
3. Observe Android Logcat with filter `tag:okhttp.OkHttpClient`.
4. Result: Continuous HTTP request and response logs flood Logcat every 6 seconds indefinitely.

Recommended Fix:
Delete `startPeriodicSync()` entirely. The application UI already observes Room DAO
`Flow`s reactively. Background synchronization, if needed, must use WorkManager with
`Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED)` and an
appropriate periodic interval (e.g., 6 to 12 hours) or be triggered exclusively by
user action (Pull-to-Refresh) and lifecycle-aware foreground collection (`repeatOnLifecycle`).

DEFECT ID: DEF-03 (MEDIUM)
--------------------------------------------------------------------------------
Classification: Confirmed Defect
File Path: app/src/main/java/com/example/smartmoney/data/remote/RetrofitClient.kt
Line Numbers: Lines 87–97
Component: `RetrofitClient.loggingInterceptor`
Description:
`HttpLoggingInterceptor.Level.BODY` is permanently configured without checking
`BuildConfig.DEBUG`.

Code Excerpt:
```kotlin
// RetrofitClient.kt: Lines 87-97
private val loggingInterceptor = HttpLoggingInterceptor().apply {
    level = HttpLoggingInterceptor.Level.BODY
}

val okHttpClient: OkHttpClient = OkHttpClient.Builder()
    .addInterceptor(authInterceptor)
    .addInterceptor(loggingInterceptor)
    .connectTimeout(60, TimeUnit.SECONDS)
    .readTimeout(60, TimeUnit.SECONDS)
    .writeTimeout(60, TimeUnit.SECONDS)
    .build()
```

Why it causes issues:
1. `Level.BODY` forces OkHttp to buffer the entire request and response into memory
   using `okio.Buffer`, converting binary bytes to UTF-8 strings for logging.
2. In production builds, logging entire payloads every 6 seconds generates massive
   heap churn, frequent garbage collection pauses, and unnecessary CPU activity.
3. While OkHttp logging itself does not transmit bytes over the mobile network, it
   magnifies battery drain and keeps the application process active in memory,
   preventing Android OS power management from putting the process to sleep.

Recommended Fix:
```kotlin
private val loggingInterceptor = HttpLoggingInterceptor().apply {
    level = if (BuildConfig.DEBUG) {
        HttpLoggingInterceptor.Level.BODY
    } else {
        HttpLoggingInterceptor.Level.NONE
    }
}
```

Description:
When the user logs in, `MainActivity` immediately creates `AccountViewModel`,
`TransactionViewModel`, `BudgetViewModel`, `HomeViewModel`, and `WarmUpSyncViewModel`.
Multiple ViewModels launch network synchronization simultaneously for the same resources
without synchronization or deduplication:
    - `WarmUpSyncViewModel`: calls `accountRepository.syncAccounts()` AND `transactionRepository.syncTransactions()`

In `MainActivity.kt`, lines 122–174 instantiate all ViewModels unconditionally inside
`setContent`. Each ViewModel's `init` block immediately triggers its respective
network calls.

Between 10 and 15 HTTP requests are fired within the first 1 to 2 seconds of application
startup. If the user navigates between screens or triggers recomposition before
coroutines settle, these calls are duplicated.

Recommended Fix:
Centralize startup synchronization inside `WarmUpSyncViewModel` or a dedicated
`SyncManager`. The other ViewModels should simply observe Room `Flow`s without
initiating remote HTTP requests in their `init` blocks.

LIKELY CAUSE ID: LIK-02 (HIGH)
--------------------------------------------------------------------------------
Classification: Likely Cause
File Path:
- app/src/main/java/com/example/smartmoney/data/remote/RetrofitClient.kt (Lines 74–85)
- app/src/main/java/com/example/smartmoney/data/remote/datasource/AuthRemoteDataSource.kt (Lines 117–142)
Component: Token Expiration & Lack of Authenticator
Description:
`RetrofitClient` has an `authInterceptor` that appends the bearer token, but does NOT
implement `okhttp3.Authenticator` or any automatic token refresh mechanism.

Behavior on Token Expiry:
When the JWT expires:
1. The backend responds with `HTTP 401 Unauthorized` or `403 Forbidden`.
2. In `HomeViewModel.startPeriodicSync()`, the exception is caught by:
   ```kotlin
   catch (_: Exception) {
       // Gracefully tolerate temporary network errors
   }
   ```
3. The loop does NOT terminate. It does NOT log out the user. It does NOT back off.
4. It sleeps for 6 seconds and retries the exact same requests with the expired token.
5. This creates an unrecoverable infinite failure loop that continues burning mobile data
   indefinitely until the app process is killed or the user logs in again.

Reproduction Scenario:
Let the user session token expire, or modify the server to return 401. Background the app.
The device will make 30–50 failing HTTP requests per minute endlessly.

Recommended Fix:
Implement an `okhttp3.Authenticator` that attempts token refresh once, and if refresh
fails, broadcasts a logout event that clears the session and terminates background loops.

RISK ID: RSK-01 (MEDIUM)
--------------------------------------------------------------------------------
Classification: Potential Risk
File Path: app/src/main/java/com/example/smartmoney/data/remote/RetrofitClient.kt
Line Numbers: Lines 94–96
Component: 60-Second Socket Timeouts
Description:
`connectTimeout`, `readTimeout`, and `writeTimeout` are all configured to 60 seconds:
```kotlin
.connectTimeout(60, TimeUnit.SECONDS)
.readTimeout(60, TimeUnit.SECONDS)
.writeTimeout(60, TimeUnit.SECONDS)
```

Risk Analysis:
While 60-second timeouts were introduced to tolerate Render free-tier cold starts,
combining a 60-second read timeout with a 6-second polling loop creates severe thread
and socket contention during network drops (e.g., entering an elevator or tunnel).
New requests are dispatched every 6 seconds while previous requests remain hung for up
to 60 seconds, consuming socket descriptors and connection pool resources.

Verification Procedure:
Simulate high-latency network (5,000ms delay) using Charles Proxy or Android Studio
Network Inspector and observe connection count in OkHttp ConnectionPool.

  is permanently destroyed (e.g. user presses Back from root or calls `finish()`).
  When the user presses the Home button, turns off the screen, or receives a phone call,
  the Activity enters `onPause()` -> `onStop()`, but is NOT destroyed.
  Therefore, `startPeriodicSync()` continues running in the background indefinitely.
- Timing Proof:
  `delay(6_000)` pauses for 6 seconds.
  Calculation:
  60 seconds / 6 seconds = 10 loop iterations per minute.
  10 iterations * 60 minutes = 600 loop iterations per hour.
  600 iterations * 24 hours = 14,400 loop iterations per day!

EVIDENCE FOR DEF-02 (N+1 UNPAGINATED HISTORICAL QUERIES):
- Location: `app/src/main/java/com/example/smartmoney/data/remote/datasource/TransactionRemoteDataSource.kt`

  Together with `getKcbTransactions` and `getAccounts`, this results in 5 HTTP requests
  every single 6-second iteration (50 requests/min, 3,000 requests/hour, 72,000 requests/day).
- Proof of Unpaginated Full Downloads:
  In `TransactionApi.kt`, lines 24–28:

  Every request retrieves all transactions for the account from day one.
